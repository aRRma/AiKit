# Проверка CLAUDE.md проекта

Только читаешь и отвечаешь. Ничего не меняй. Сборку, тесты и приложение не запускай, субагентов не вызывай.

## Порядок

1. **Репозиторий.** Путь из аргументов, иначе текущая папка. Найди в нём `CLAUDE.md`, `CLAUDE.local.md`, `.claude/CLAUDE.md`, `.claude/rules/*.md` и файлы, которые они подключают через `@путь`. Нет ни `CLAUDE.md`, ни `.claude/CLAUDE.md` — скажи это одной строкой и остановись.
2. **Пункты.** По каждому пункту чек-листа найди правило и поставь статус:
   - `Есть` — правило есть, и по нему можно работать без вопросов.
   - `Неполно` — правило есть, но нет части из столбца «Что должно быть». Назови, какой части нет. Часть, которая не нужна проекту, не считай.
   - `Ссылка` — в CLAUDE.md только ссылка, правило лежит в другом документе. Для пунктов 1–3 ставь `Неполно`: команды нужны в самом CLAUDE.md, он грузится всегда. Команды в CLAUDE.md, а подробности по ссылке — это `Есть`.
   - `Нет` — правила нет. Перед этим статусом ищи по смыслу, а не по одному слову: правило может стоять в другом разделе и на другом языке.
   - `Сломано` — правило называет файл, папку, проект или команду, которых нет.
   - `н/п` — пункт не нужен этому проекту. Назови причину.
3. **Пути.** Каждый файл, папку, решение и проект из найденных правил проверь через Glob (папку — маской `<папка>/*/*` или `<папка>/*`), раздел документа — через Grep. Путь с заполнителем (`<n>`, `<taskId>`) проверяй по родительской папке. Не нашёл — `Сломано` и маска, по которой искал. Глубже «существует» не проверяй: смысл правил сверяет `/arrma-verify-claims`.
4. **Противоречия.** Сверь найденные правила между собой и с `~/.claude/CLAUDE.md` и `~/.claude/rules/*.md`. Противоречие назови с обеими строками. Какая строка верна, не решай.
5. **Предложения.** Для `Нет`, `Неполно` и `Сломано` дай готовые строки для CLAUDE.md и раздел, куда их вставить. Пиши строки на языке и в стиле этого CLAUDE.md, не по STE. Факты бери только из репозитория (README, документация, файлы решения, CI, `.env*`, `launchSettings.json`) и указывай `file:line`. Файл, который CLAUDE.md называет неверным источником или запрещает, источником не считай. Факта нет — пиши `<уточнить: …>`, не выдумывай.

## Чек-лист

Критичные: без них агент ошибается или переспрашивает.

| № | Пункт | Что должно быть |
|---|---|---|
| 1 | Сборка | точная команда сборки решения или проекта; флаги, без которых сборка ломается |
| 2 | Тесты | команда для всех тестов и для тестов затронутого кода (проект или фильтр); условия: env-файл, Docker, VPN, база; признаки сбоя среды (какая ошибка значит, что нет Docker, сети или базы); живые проверки, которых проект требует для области кода (запуск приложения, UI); тесты, которые падают намеренно, и как их исключить; какие тесты CI не запускает |
| 3 | Запуск | команда запуска каждого приложения, кроме тех, что запускать нельзя; адрес и порт; имя окружения; признак успешного старта; что запускать нельзя |
| 4 | Папка задач | путь к папке задачи, если он не `docs/tasks/<задача>/`; файлы `requirements.md`, `analysis.md`, `plan.md`; как отличить задачу старого формата; где записаны решения и принятые риски, чтобы проверка не считала их находками; что делать с папкой после слияния |
| 5 | Язык | язык ответов в чате, файлов задачи, документации проекта, комментариев и XML-doc, логов, текстов UI, сообщений коммитов |
| 6 | STE | какие тексты пишутся по STE (скилл `arrma-ste`) и какие нет; где глоссарий проекта |
| 7 | LSP | навигация по коду через LSP и как его загрузить (`ToolSearch` с `select:LSP`); когда нужен текстовый поиск; известные ложные результаты LSP |
| 8 | Git | базовая ветка; имя ветки; формат коммита; коммит и push только по просьбе |
| 9 | Документация | где лежит документация проекта; какой файл читать для какой области; правило обновлять документацию в той же задаче, что и код |
| 10 | Запреты | файлы, папки и сборки только для чтения; скрипты и приложения, которые нельзя запускать; код, который нельзя удалять, хотя он выглядит неиспользуемым |

Желательные:

| № | Пункт | Что должно быть |
|---|---|---|
| 11 | Оболочка и файлы | команды для Bash или PowerShell; кодировка, BOM и концы строк; чем править файлы |
| 12 | Выкат | порядок и способ выката; где записывать миграции базы, индексы и новые ключи конфигурации: `/arrma-task-summary` берёт выкат только из CLAUDE.md и документации |
| 13 | Учётные данные | какие пароли и строки подключения лежат в репозитории намеренно, чтобы проверка не считала их утечкой |
| 14 | Вопросы | неясное бизнес-правило — спросить пользователя, не выдумывать |
| 15 | Сверка цитат | строка `Команда сверки цитат: …`. Нужна, только если есть `~/.claude/tools/check-claims/check-claims.dll`; иначе `н/п` |

## Итог

1. Таблица «№ | Пункт | Статус | Где (`файл:строка`) | Что не так». Для статуса `Есть` столбец «Что не так» оставь пустым.
2. «Противоречия» — только если есть.
3. «Предлагаю добавить» — готовые строки по пунктам: сначала критичные.
4. Одна строка: сколько пунктов в каждом статусе.

Ответ читает пользователь: пиши на русском и по STE, кроме строк для CLAUDE.md. Если скилл `arrma-ste` в этой сессии ещё не загружен, сначала загрузи его.
